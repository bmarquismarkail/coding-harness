# v0.2 guide

The shared `Harness` service implements submission, status, event pages, results, artifacts, resume, cancellation, and run listing. The batch CLI, Python API, and MCP tools use this implementation. A main model is the sole writer; up to nine read-only specialists investigate focused scopes. Specialists cannot edit, run project code, or delegate.

## Setup and models

Use `/home/user/python-venv/langchain-suite/bin/python`. Install the package with `python -m pip install -e .` if using it outside this directory. Linux, Git, and Bubblewrap (`bwrap`) are required. Dependencies include `mcp==2.3.0` and `langgraph-checkpoint-sqlite==3.1.2`. Python and C/C++ checks use installed toolchains; other languages use configured commands and read-only dependency mounts.

The existing `agent-config.json` is unchanged:

| Role | Base URL | Model |
| --- | --- | --- |
| Main | `https://lead.example.invalid/v1` | `JetBrains/Mellum2-12B-A2.5B-Thinking` |
| Specialists | `https://specialist.example.invalid/v1` | `XHToken/Spark-X2.6-4B` |

Both read `LLAMA_API_KEY` from the environment and send a Bearer token. Model URLs must not contain credentials or query parameters. Existing `MAIN_BASE_URL`, `MAIN_MODEL`, `SUBAGENT_BASE_URL`, `SUBAGENT_MODEL`, and `SUBAGENT_PARALLELISM` environment overrides remain available. Submitted jobs freeze their effective model configuration; later configuration changes do not silently change their model identities.

## CLI

```bash
python -m coding_agent.cli submit --root /path/to/project \
  --checks acceptance-checks.json 'Repair the parsing failure'
python -m coding_agent.cli run --wait --root /path/to/project \
  --checks acceptance-checks.json 'Repair the parsing failure'
python -m coding_agent.cli status RUN_ID
python -m coding_agent.cli events RUN_ID --cursor 0 --limit 20
python -m coding_agent.cli result RUN_ID
python -m coding_agent.cli artifact RUN_ID ARTIFACT_ID --offset 0 --limit 8000
python -m coding_agent.cli list-runs --limit 20
python -m coding_agent.cli resume RUN_ID
python -m coding_agent.cli resume RUN_ID --answer 'Preserve the Python 3.11 API'
python -m coding_agent.cli cancel RUN_ID
```

Submission returns a run ID immediately. `run --wait` exits 0 only for a verified result; read operations exit 0 when the operation succeeds. Waiting can also end with `needs_input`, `interrupted`, `failed`, or `cancelled`. Resume continues an interrupted graph or answers its persisted question. Cancellation is terminal and retains completed work. Interrupted commands remain unverified until rerun; interrupted edits reconcile their exact action receipt and source hashes before replay.

All commands accept `--state-dir` and `--config`. `--mode review` investigates without patch tools or automatic project execution. `--task-type` selects `bugfix` (default), `feature`, or `refactor`. Select named profiles with `--profile`; add specific read-only dependencies with repeated `--dependency` options.

Project profiles are loaded from `project-profiles.json` or the optional `project_profiles` configuration object. A matching repository root is selected automatically; `--project-profile` can select one explicitly. Profiles supply default registered checks and skill IDs. An omitted `--checks` uses profile checks; an explicit JSON file, including `[]`, replaces them. Repeated `--skill` options replace profile skills, and `--no-skills` disables them. Python callers use `TaskRequest(project_profile=..., skill_ids=..., checks=...)`; MCP submission exposes the same fields. Skills are loaded from repo-local `.agents/skills`/`.codex/skills`, `~/.agents/skills`, or `~/.codex/skills`, copied into the immutable run configuration as read-only `SKILL.md` snapshots, and identified in the run result by source path and content hash. Missing or oversized skills fail submission.

Check files are JSON arrays. Commands use argument arrays, never shell strings:

```json
[
  {"id":"acceptance","kind":"acceptance",
   "argv":["python","-m","unittest","discover","-s","tests","-p","test_reproduction.py"]},
  {"id":"regression","kind":"regression",
   "argv":["python","-m","unittest","discover","-s","tests"]}
]
```

For C/C++, supply a build check followed by an executable check with `requires: ["build-id"]`. Prerequisites must occur earlier in the check list. Put output binaries under `build-*`, which is excluded from source hashes and patches. If no regression suite is supplied, Python projects with unittest tests receive discovery checks; CMake projects receive configure/build/CTest checks. CTest uses `--no-tests=error`. Other build/test conventions need explicit commands.

## Python API

```python
from coding_agent import CheckSpec, Harness, TaskRequest

harness = Harness(config_path="/path/to/agent-config.json")
run_id = harness.submit(TaskRequest(
    root="/path/to/project",
    task="Repair iterator handling while preserving the public API",
    checks=[CheckSpec(id="acceptance", argv=["python", "-m", "unittest", "tests.test_iterators"])],
))
status = harness.wait(run_id)
events = harness.events(run_id, cursor=0, limit=20)
result = harness.result(run_id)  # RunResult, or None before a result exists
```

The same object exposes `status`, `events`, `artifact`, `resume`, `cancel`, and `list_runs`. `Harness(..., profiles={...})` configures named profile overrides. `autostart=False` queues jobs without starting a supervisor, for controlled evaluations. MCP server instances enforce repository and dependency roots through this service.

## MCP

SDK v2's `MCPServer` exposes eight tools over both transports: `harness_submit`, `harness_status`, `harness_events`, `harness_result`, `harness_artifact`, `harness_resume`, `harness_cancel`, and `harness_list_runs`.

Configure a stdio client to launch:

```bash
/home/user/python-venv/langchain-suite/bin/python -m coding_agent.cli serve-mcp \
  --transport stdio --config /path/to/agent-config.json \
  --allow-root /path/to/projects
```

For Streamable HTTP:

```bash
export HARNESS_MCP_API_KEY='a separate MCP credential'
python -m coding_agent.cli serve-mcp --transport streamable-http \
  --allow-root /path/to/projects
```

HTTP defaults to `http://127.0.0.1:8765/mcp`. Every request requires `Authorization: Bearer $HARNESS_MCP_API_KEY`. A model credential alone does not authorize MCP access. Localhost hosts are allowed by default; browser origins are rejected unless configured. Use repeated `--allowed-host hostname[:port]` and `--allowed-origin https://client.example` for a TLS reverse proxy. Use `--allow-dependency` for each permitted dependency root. Reverse-proxy deployment and multiple-user authorization are outside this version.

Submit takes `{"request":{"root":"/allowed/project","task":"...","mode":"implement"}}`. Poll the returned run ID. Event pages return `next_cursor`; artifacts return `next_offset` and `has_more`. MCP results expose patch artifact IDs instead of embedding patches or transcripts. Disconnecting a client does not stop its durable job.

## Profiles and budgets

| Profile | Main thinking | Purpose |
| --- | --- | --- |
| `coding` | Disabled | Direct implementation actions |
| `review` | Disabled | Investigation/review |
| `deep` | Enabled, 8192 output tokens | Main-model reasoning |
| `legacy` | Existing configuration | Preserve original request settings |

Specialists use thinking-disabled settings in the new coding/review/deep profiles. Defaults are nine concurrent specialists, 200 tool/check actions, 200 model requests, 60 minutes of active execution, 300 seconds per model request, and 600 seconds per command. Model requests and tool actions have separate recorded counters; malformed responses still consume the model-request budget. All limits are recorded per run. Resume does not reset consumption. Explicitly switching profiles starts a new graph revision and invalidates specialist reuse across profile changes, while preserving the workspace and receipts. There is no automatic model switch or budget increase.

Add a `profiles` object to a complete JSON configuration, or pass the equivalent dictionary to `Harness(profiles=...)`. Named overrides accept fields in `coding_agent.types.Profile`:

```json
{"profiles":{"connected":{
  "allow_network":true,"allow_install":true,
  "max_actions":200,"max_active_seconds":3600
}}}
```

Actions use schema-constrained JSON supported by llama-server and are validated again by the tool broker. Servers without schema support may explicitly use profile `constrain_actions: false`; validation remains mandatory. Main and worker context byte budgets are separate; full observations remain recoverable by artifact ID after compaction.

## Workspaces and execution

State defaults to `$XDG_STATE_HOME/coding-agent`, or `~/.local/state/coding-agent`. A detached supervisor holds an OS lock and admits one active job at a time. Each run retains its effective baseline, workspace, LangGraph SQLite checkpoints, receipts, specialist conversations, immutable artifacts, and process logs. State is outside the selected repository. Existing tracked development evidence stays unchanged.

Git projects use detached worktrees seeded with relevant uncommitted files. A private baseline index captures that effective checkout without commits or source-index changes. Non-Git projects, subdirectory selections, and unborn Git repositories use filtered copies. File modes are retained. Secrets, VCS metadata, generated outputs, caches, and historical development evidence are excluded. Source symlinks and files above 10 MiB fail explicitly; provide a separately materialized fixture when needed. Retained workspaces and worktree registration remain available for inspection; there is no automatic deletion.

Bubblewrap exposes writable job storage and temporary storage, read-only toolchains/dependencies, and a sanitized environment without model or MCP credentials. Network is disabled by default. Installers require an explicitly enabled profile; even then, the shared host toolchain stays read-only, so use a job-local environment. Sandbox startup failure stops execution; there is no host fallback. Model HTTP requests occur outside the project sandbox.

Project instructions and build metadata are read before investigation. Nested `AGENTS.md` files must be read before editing their scope. Semantic search navigates existing indexes with refresh disabled, then issues fresh source-bound evidence. Missing indexes and changed files use exact search/current reads. Index creation remains explicit through the legacy zvec CLI/API, preserving `ZVEC_GREP_EMBEDDING`.

## Verification

The verifier requires final frozen checks to pass on the final source hash, executable acceptance checks, and relevant existing regression coverage. Bug fixes/features must demonstrate an acceptance failure on baseline sources; refactors must pass baseline acceptance. Original tests/build oracles and registered additional tests are hash-protected. Changes to source during checks, skipped prerequisites, truncated output, stale citations, missing checks, exhausted budgets, incomplete responses, and unresolved review gaps prevent verification. A fresh review is required when specialists are enabled.

Workflow state and verification outcome are separate: `completed` can have outcome `unverified`. Review findings stay hypotheses until independently established. Agreement between models is not proof. Review jobs report unverified hypotheses rather than verified implementation success. The readable report and structured result identify the patch, executed checks, artifacts, and remaining gaps.

Each result also includes an `evidence` package with baseline check outcomes, reproducer artifact IDs, diagnosis text and source evidence IDs, the patch artifact and final source hash, candidate verification outcomes, skill snapshot metadata, and remaining gaps. A bugfix or feature still needs a baseline-failing acceptance check; a refactor needs baseline-passing acceptance. Diagnosis citations must point to current source evidence. Missing, stale, or invalid citations keep the result unverified. The result's `evidence_ids` field retains the broader artifact references used during the run.

Arbitrary configured check commands cannot be proven semantically adequate by the harness. Supply trusted acceptance checks and inspect the patch/report. Original build configuration changes conservatively invalidate automatic verification. The harness returns patches for review; it does not apply them to the selected checkout, commit, push, or open pull requests.

## Evaluation

```bash
PYTHONDONTWRITEBYTECODE=1 python -m unittest discover -s tests -v
RUN_V2_LIVE=1 PYTHONDONTWRITEBYTECODE=1 \
  python -m unittest discover -s tests -p test_v2_live.py -v
```

The ordinary suite uses real Bubblewrap Python/C++ repairs and real MCP clients over stdio and HTTP with a deterministic local model server. It covers restart, partial edits, interrupted commands, cancellation, stale evidence, malformed actions, sandbox boundaries, and retained Proto-Time false-positive cases.

Live acceptance uses both configured models without manual patching or synthesis assistance and independently grades resulting source. Every attempt, including failures, is retained under `~/.local/state/coding-agent-acceptance`; override with `HARNESS_LIVE_EVIDENCE_DIR`. Ordinary discovery skips live inference. The original v0.1 live handoff test remains opt-in via `RUN_LIVE_MODEL_TESTS=1`, preserving its historical evidence format.

See [architecture.md](architecture.md) for persistence/trust boundaries and [mcp-evaluation.md](mcp-evaluation.md) for interface evaluation scenarios.

The [implementation evaluation report](evaluation-results.md) distinguishes the passing deterministic suite from the retained failed live acceptance attempts.
