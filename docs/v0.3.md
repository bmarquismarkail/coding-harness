# v0.3 evidence and review contracts

The legacy `outcome` remains the implementation acceptance gate. `review.completion` describes process completion. A partial review can contain reproduced observations, and a completed review can contain unresolved hypotheses.

## Evidence pipeline

`ImmutableEvidenceBundle → ReviewerEvidenceView → ReviewerResponse`

Every bundle and view is an immutable artifact in the run's own artifact directory. Bundles retain complete references and snapshot identity. Views contain bounded excerpts and an omission manifest. When a specialist reads additional source, finalization freezes a successor bundle before adjudicating its response. Earlier bundles and views remain retained. A missing excerpt in a view does not mean that its underlying evidence is absent.

The result's `review` field includes bundle and adjudication references, findings, coverage, completion, and partial reasons. CLI, Python, and MCP use the same result contract. Older stored results default to `review=null`.

Reviewers return `findings`, `observations`, `challenges`, and `semantic_concerns`. A finding requires `id`, `title`, `claim`, and `path`, with source range, phase, severity, citations, and optional `defect_id`. Factual challenges use `check_missing`, `check_passed`, `source_exists`, or `source_examined`. For `source_examined`, supply the `view_id` shown in the reviewer prompt. The adjudicator requires the source excerpt to be included in that registered view. Mechanical decisions retain the original proposal and referenced bundle. General concerns about test adequacy remain unresolved semantic concerns.

Legacy empty reports remain supported. Unstructured legacy findings fail closed. The historical fixture retains the original report and migrates its observation and missing-check assertions to typed fields. Each migrated assertion is adjudicated once. Unmapped legacy gaps and typed semantic concerns remain blocking.

## Trusted probes

`TaskRequest.defect_probes` accepts caller-controlled definitions, also configurable in project profiles. Each definition supplies a stable `defect_id`, narrow `observation`, check ID, snapshot-specific target path/range, `phase`, exact `source_hash`, Python `wrapper` bytes, and disjoint observed/not-observed exit codes. Use one probe per configured check. The harness freezes the definition, check specification, and wrapper at submission.

The wrapper runs under isolated Python in Bubblewrap, mounted read-only at `/trusted-probe.py`, with the original check argv available as arguments. Its author must distinguish observed behavior from generic process failure. The wrapper may inspect sources or run a checked executable and translate its outcome into the declared signals. A model cannot register a trusted definition through a tool.

A completed valid execution with an observed signal produces `reproduced` for the registered observation. The model's explanation remains separately recorded. Missing execution, changed target snapshot, invalid prerequisites, timeout, source modification, cancellation, or truncated output is inconclusive. A successful absent signal leaves the proposal a hypothesis. Moving a source file requires a new snapshot-bound target and execution.

## Investigation

Dependency discovery defaults to 2,000 edges, 200 paths, 4 MiB, and two monotonic elapsed seconds. Patch paths, requested focus paths, and discovered dependencies take priority over background source scans. A review without a focus starts with the whole inventory as its intended scope.

Coverage uses `limit_reached` for a stop that leaves known scope unfinished and `omitted_paths` for known targets excluded from intended scope. Such a stop makes review partial and blocks implementation verification. An optional inventory scan can stop at `scan_limit_reached` after known work is complete. `unscanned_paths` lists inventoried files without a completed discovery scan, including an interrupted file. `unenumerated_remainder` indicates that undiscovered relationships may remain.

A focused review can complete after an optional scan stops if every intended path has valid source-read evidence and the other review gates pass. For a deleted file, a valid baseline read counts. Implementation acceptance still requires its checks, finding resolution, and protocol gates. Lexical discovery can miss dynamic dependencies.

Progress counts newly covered in-scope source intervals per file hash and phase, distinct check outcomes, and source changes. Global action/request/time budgets still apply. Three consecutive protocol failures exhaust recovery by default. `report_findings` persists typed drafts for interruption and exhaustion. These records are re-adjudicated against retained evidence when producing partial results. During implementation finalization, investigative drafts stay in the run history. Findings asserted in the final writer or reviewer response must still be resolved.

## Qualification

Run provider-free acceptance with:

```sh
PYTHONDONTWRITEBYTECODE=1 python -m unittest discover -s tests -v
```

Bubblewrap and deterministic loopback HTTP fixtures require a host environment that permits namespaces and local sockets. Live tests require their existing explicit environment opt-ins.

`coding_agent.qualification.prepare_fixtures(path)` prepares six fixed Python, C11, and C++17 defective/clean review tasks. It stores request and gold manifests outside each target source directory, plus 100 predetermined list/read/finish protocol opportunities. Pass `protocol_opportunities=1000` when preparing a larger campaign. Fixture preparation invokes no model. Keep gold manifests outside model-visible task roots.

`python -m coding_agent.qualification measurements.json` summarizes previously collected measurements. Input contains `purpose`, `configuration`, `protocol` (boolean attempt lists per opportunity, maximum three attempts), `cases` (IDs, language, expected and detected defect IDs, unsupported critical count), and `promotions` (evidence-validator booleans). Expected IDs represent curated high/critical defects. Empty lists of attempts represent timeouts or no response. The reporter rejects duplicate case IDs.

The report gives first-response and bounded-recovery rates, recall, clean-case false positives, promotion fidelity, counts, Wilson 95% intervals, and individual failed opportunities. Smoke runs require 100 opportunities. Comparison/release runs require at least 1,000. Observed gates and statistical confidence are separate. Empty promotion evidence cannot satisfy the promotion gate. These reports summarize supplied measurements and do not authenticate a model campaign or establish unattended readiness.

Live model campaigns require fresh approval for the particular experiment. Model thinking and specialist concurrency retain their configured defaults.
